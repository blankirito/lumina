# Production backup implementation — execution locked pending Decision 1

Owner must approve the destination, region, custodians, retention, budget and restricted restore target before any production data is read or copied. This document is an implementation recipe, not an existing backup. The checked-in recovery executable accepts only `udhymvnzvsejrzpuninp`; do not remove that guard to use it on production.

## Recommended launch baseline

Independent encrypted daily checkpoints covering all components below, plus a checkpoint immediately before the release migration window. Proposed launch objectives: complete checkpoint RPO <=24 hours and measured end-to-end RTO <=4 hours. These are acceptance targets, not achieved promises. If losing a day's confirmed orders is unacceptable, the owner must select a shorter interval or PITR before launch. PITR improves database recovery only; the object/configuration checkpoint still bounds complete-system recovery.

Prefer a hybrid of Supabase Pro daily database backups and independent encrypted DB/Auth/Storage/configuration copies. Free independent backup is a viable budget alternative only after the same restore gate passes and an always-available runner, offsite destination and named responder exist. A laptop that might be asleep is not a reliable scheduled runner. No plan has been purchased.

Official prices verified 2026-10-22, USD, before tax, overages and external runner/storage charges: Pro starts at $25/organization/month, $10 compute credit; two Micro projects in the organization are approximately $35/month ($25 + $10 + $10 - $10). Pro daily database retention is 7 days. PITR requires at least Small compute: 7/14/28-day retention costs approximately $100/$200/$400 per month; production Small plus staging Micro with 7-day PITR is approximately $140/month. These estimates assume no other projects, discounts or add-ons. Recheck the billing quote before authorization. Independent backup has no Supabase backup add-on fee, but bandwidth, destination, runner and operator time are not automatically free. R2's published free tier is 10 GB-month, 1 million Class A and 10 million Class B operations; retained encrypted snapshots can exceed it quickly.

## Required checkpoint contents and procedure

1. **Pin identity and stop side effects.** Authorized source must be exactly `xsjcmrlwdpudrkjhghdl`, cross-checked against the management project and database identity over TLS. Pin CLI/PostgreSQL client versions; source is PostgreSQL 17. Configure a dedicated, access-controlled runner with disk encryption, private temporary directory and no shell tracing. Never put credentials in arguments, logs, source control or PR artifacts. Use secret-manager injection and a restricted database connection. Record start time, source project, application commit and migration checksums.
2. **Create a consistent recovery cut.** During the first pre-release backup, block writes at the effective entry points, drain old Preview/Production clients and database/QR jobs, wait for in-flight operations and pause Auth changes/uploads. A page banner does not stop APIs, old deployments or cron. Record the cut time. Ongoing online copies need a consistent exported PostgreSQL snapshot plus a reconciliation pass for object mutations; independent file copies taken at unrelated times must not be labelled one consistent recovery point. Do not resume old workers against the new QR schema.
3. **PostgreSQL data and schema.** Use a PostgreSQL 17-compatible `pg_dump` custom-format full database archive with a consistent snapshot. Preserve functions, types, triggers, RLS policies, grants, extensions, sequences and ownership information; capture required role definitions separately without copying platform-managed role passwords. Inventory every included schema, including `public`, `auth`, `storage` and `supabase_migrations`; check the archive table of contents and errors, not just process exit. Supabase CLI's ordinary dump defaults omit managed Auth/Storage schemas, so a default CLI export is not a complete backup. Record customizations separately from platform-managed baseline definitions and test the explicit restore selection against a matching Supabase baseline. Never blindly overwrite platform-owned schema definitions on a fresh managed project. Unknown/unrestorable entries fail the checkpoint.
4. **Auth state.** Include users, password hashes, identities, confirmation/ban state and all enabled factor/provider-related tables. Keep Auth UUIDs identical to application owners/members/customers. Treat hashes and token-bearing tables as secrets. Recovery defaults to invalidating sessions/refresh tokens and requiring reauthentication; do not promise existing JWTs survive a new project's signing keys. Isolate restored email/SMS/OAuth endpoints, disable outbound deliveries and scheduled side effects before any data load. Exercise password sign-in, confirmation state, identity joins and reset using designated controlled accounts, never by logging in as a customer. MFA/provider recovery and any root-encryption-key dependency must be explicitly verified if enabled; preserve required key material separately in approved escrow.
5. **Storage metadata AND bytes.** Inventory each bucket's public/private status, size/MIME limits and policies. Capture every referenced object with bucket, exact key, version when supported, byte length, MIME/cache metadata, logical owner, SHA-256 and encrypted destination key. Download actual bytes through an approved API/S3 path using a scoped backup credential. Match the inventory to the database cut; retry changed versions and fail on missing bytes. Copy bytes to immutable backup keys, never a destructive mirror. Retain versions referenced by any retained checkpoint even when their live object is deleted. Raw `storage.objects` rows alone cannot recreate files. Restore via supported Storage upload/import, then reconcile logical owner/policies; generated object IDs, etags and versions may differ, and must not be fabricated by direct Storage table writes. Verify the complete byte inventory and tenant access rules.
6. **Configuration and secrets.** Version an encrypted configuration manifest: Vercel project/build/runtime/region, domain/DNS, environment variable names and environment bindings, Supabase settings/extensions/cron, Auth redirect allowlist/site URL/SMTP/providers, bucket configuration, firewall/rate limits/alerts and worker schedules. Store actual secret values or recoverable secret-manager version references in separate escrow accessible to the recovery custodians. A list of variable names is not a restorable configuration. Never reuse production service keys in public Preview. Restore disabled integrations first; enable them only during the approved cutover.
7. **Encrypt and commit.** Stream production-sized exports through an authenticated, established encryption tool (for example age with an approved recipient), rather than the small in-memory synthetic bundle format. Encrypt before offsite transfer, authenticate transport and verify downloaded ciphertext. Use separate source-read, destination-write and restore/decryption identities; append-only writer cannot delete backups or read the decryption key. Escrow the private key separately with a second named custodian and test key recovery. Commit a manifest/checkpoint only after all mandatory components and hashes pass. Failed/incomplete runs remain visibly failed, never replace the last good point and trigger the assigned responder.
8. **Retention.** Proposed minimum: 30 daily complete checkpoints plus 12 month-end checkpoints, and retain the pre-release checkpoint until the release is accepted. Confirm privacy/deletion requirements before authorizing these periods. Retention applies to DB/Auth, configuration and referenced object versions together. Keep the latest verified point even when overdue; preserve unverified runs for investigation, with a separately approved cleanup policy. Independent deletion credentials and a grace period protect against compromised backup jobs. The included retention function is a plan only and performs no deletion.

## Restore acceptance — required before B3 closes

Use a dedicated restricted recovery environment approved for production data; do not load production records into the ordinary developer staging project. Confirm blank target, exact identity, same PostgreSQL/Supabase compatibility and disabled integrations before restore. A platform clone may start cron immediately; do not choose cloning if isolation cannot be established first.

Restore the tested baseline/platform services, custom schema and approved roles; load Auth and application data in dependency order, sequences and migration history; recreate policies/grants/triggers; import Storage bytes/configuration and reconcile metadata. Apply only the version-compatible application artifact. No blind replay of 001–044 and no snapshot-derived permission expansion.

Acceptance evidence: all required archive entries restored without ignored errors; schema/ACL/RLS/function/extension checks; relational integrity and sequence checks; matching table counts/checksums in the restricted environment without publishing customer values; all Storage object counts/lengths/SHA-256 verified; controlled-account sign-in/reset and tenant-isolation checks; checkout/payment/inventory/QR lifecycle on dedicated synthetic records; sessions handled under the declared policy; required config/secrets recoverable; ciphertext tamper/wrong-key rejection; measured elapsed recovery time <= accepted RTO. Record age of the last complete consistent checkpoint as actual RPO. Send and receive a real backup-failure/freshness alert. Schedule monthly restore verification and one after material schema/Auth/Storage changes. Cleanup/expiry of the restored production copy is part of Decision 1.

## Staging evidence and limits

2026-10-22: a newly generated synthetic owner, inactive store and draft product were captured with Auth state, schema inventory, migration inventory, bucket configuration, exact object metadata and actual PNG bytes. Six components were AES-256-GCM encrypted locally under a random separate key. Stock and password were deliberately changed; the original login failed, then stock/password were restored from the authenticated archive and login succeeded. The image was deleted, absence observed, bytes re-uploaded and SHA-256 matched. The restored metadata owner matched the synthetic user. No production data was read/exported.

The first real Storage deletion exposed a missing owner/admin SELECT policy; the hardening migration fixed it on staging. Local regression checks prove another store remains inaccessible. Staging recorded this migration as `20261022025242`; repository file is `20261022023729_release_privilege_hardening.sql`. Preserve this explicit mapping during ledger reconciliation, rather than treating the different timestamp as an unapplied second migration. The earlier checkout recovery mapping remains repository `20261021151151` -> staging `20261021151906`.

This probe restores selected existing-row fields and one object. Its schema component is an inventory, not restorable DDL. It does not certify a full managed database rebuild, production capacity, session/MFA continuity, independent destination/key escrow, monthly retention execution or a 4-hour production RTO. Those are concrete Decision 1 acceptance tasks, not reasons to repeat the broad audit.
